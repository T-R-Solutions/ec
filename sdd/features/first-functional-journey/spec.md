## Escopo e contrato v1alpha1

REQ-01: configuração canônica YAML de um projeto e um pipeline de uma etapa, sem DAG, triggers, herança ou plugins. `apiVersion: ec/v1alpha1`, `kind: ProjectPipeline`, `project`, `pipeline`, `repository`, `commit`, `script`, `timeoutSeconds`, `artifact`. Todos obrigatórios; nomes ASCII minúsculos/hífen até 64 caracteres, commit Git SHA-1 de 40 dígitos hexadecimais, repositório local absoluto controlado pelo operador, script até 8192 bytes, timeout decimal entre 1 e 3600 segundos (aspas aceitas; o schema define a interpretação numérica), artefato relativo sem traversal. Repositórios remotos e credenciais VCS ficam para próxima revisão de schema. O operador configura allowlist fora do YAML antes de habilitar execução. O schema sozinho não autoriza caminhos ou execução.

Parser aceita um documento UTF-8 até 64 KiB, profundidade até 16, até 4096 eventos e escalares até 8192 bytes. São limites conservadores iniciais, sem promessa de capacidade. Rejeitar chaves duplicadas antes de criar mapas, chaves complexas, aliases, anchors, tags, merge keys, campos desconhecidos, null e coleções nos campos escalares. Credenciais/sessões não possuem campos; segredos literais dentro de scripts arbitrários não são detectáveis genericamente: a política inicial proíbe fornecê-los. Suporte a referências de segredos e sua resolução ainda precisa ser implementado antes de aceitar jobs que precisem de credenciais. Comentários não fazem parte do modelo; editor deverá preservar texto original ou apresentar diff antes de reserializar.

REQ-02: revisão imutável identifica bytes YAML por SHA-256; configurações desejadas têm autoridade nos bytes versionados, projeções são reconstruíveis. Publicação recebe request ID, base revision e YAML; autenticação e autorização precedem efeitos. Na transação PostgreSQL: bloquear projeto, comparar base, inserir revisão imutável e projeção, atualizar publicada/efetiva e recibo. Neste recurso sem efeitos externos, publicada e efetiva podem avançar na mesma transação, com campos distintos. Antes de commit, queda reverte; depois de commit, repetir request ID retorna recibo idêntico ou rejeita payload diferente. Preferência futura por Git para configuração exige mecanismo de reconciliação separado; não há dupla gravação banco/Git neste primeiro fluxo proposto.

REQ-03: usuário possui identidade opaca, sessão expirada/revogada é rejeitada. Papéis iniciais viewer/operator/admin por projeto; viewer apenas lê. Agent possui identidade e credencial separadas, nunca sessão de usuário. Segredos por referências resolvidas fora do YAML, ainda pendentes. Server decide acesso por ação/recurso. Operação negada não grava revisão, fila, logs nem recibo de sucesso. HTTP `/api/v1`, erros JSON com code/message/requestId; 400 sintaxe, 401 sessão, 403 permissão, 404 recurso autorizado ausente, 409 conflito/fence/requestId, 422 regra ou referência, 413 limite. IDs fornecidos pelo cliente não autenticam.

REQ-04: execução fixa revisionId/configHash e commit SHA completo na submissão; edição posterior não os altera. Run: queued → assigned → running → succeeded/failed/timed_out/cancelled; cancel_requested é intenção persistida separada, exibida até confirmação. Attempt tem ID, ordinal, agentSessionId, fence crescente, leaseUntil e receipt. Capacidade inicial Linux com um slot anunciado. Agent registra e estabelece sessão autenticada; reinício cria sessão nova e invalida a anterior. Reserva bloqueia slot e job em uma transação PostgreSQL; nenhum slot pode possuir duas tentativas ativas. Heartbeat renova somente lease/fence/sessão vigentes. Lease vencido perde autoridade antes de reatribuição. Retry por perda de lease, máximo duas tentativas; falha de script não recebe retry automático. Podem repetir efeitos externos. Cancelamento e conclusão disputam o mesmo lock; cancelamento confirmado vence se solicitado primeiro; conclusão já commitada torna cancelamento sem efeito com resposta explícita. Resultado obsoleto é rejeitado. Replay do resultado aceito devolve recibo persistido; divergência no payload é conflito. Reconexão consulta tentativa e recibos antes de executar novamente.

REQ-05: workspace por tentativa; checkout verifica HEAD igual ao SHA fixado. Execução confiável local, sem isolamento alegado. Preparação falha antes de running; processo e descendentes recebem término no timeout/cancelamento, com causa distinta de exit code. stdout/stderr drenados independentemente; logs contêm run/attempt/step/stream/sequence, chunks até 64 KiB e total até 16 MiB por tentativa com truncamento explícito. Persistir chunk e ack juntos; replay igual é idempotente, divergente é conflito. Finalização inclui último sequence confirmado. Artefato até 16 MiB: staging, tamanho/hash esperados, finalização verifica bytes e publica identidade imutável em transação; incompleto/corrompido não aparece como íntegro. Downloads exigem acesso ao projeto. Retenção e controles para jobs não confiáveis permanecem planejados.

REQ-06: Vue 3/TypeScript/Pinia oferece projetos, configuração, execuções e agentes. Visual estruturado de uma etapa, formulário e YAML usam mesmo modelo; YAML inválido mantém último modelo válido e diagnóstico. Rascunho, validação local, pedido enviado, aceito, iniciado, finalizado e confirmado têm rótulos separados; frontend não infere confirmação pela ausência de erro. Teclado e foco, estados vazios/erro/acesso negado/desconectado devem ser exercitados no navegador com API real.

## Contrato da publicação persistente — 2026-11-05

REQ-01/02/03: projeto e pipeline usam nomes do schema; criação inicial administrativa local cria projeto vazio e grant admin, sem revisão. Pipeline nasce na primeira publicação; a revisão base é global por projeto (0 vazio). POST /api/v1/projects/{project}/publications recebe JSON estrito {requestId, baseRevision, yaml}; requestId ASCII alfanumérico/hífen, 1–64 bytes. GET /api/v1/projects/{project} retorna ponteiros; GET /api/v1/projects/{project}/revisions/{revision} retorna YAML textual exato, SHA-256 e projeção; GET /api/v1/projects/{project}/receipts/{requestId} recupera recibo da própria identidade.

Request ID tem escopo identidade/projeto, retenção indefinida nesta fatia. Payload igual significa mesma base e mesmos bytes UTF-8 YAML; replay exige permissão atual de publicar e retorna recibo original. Reuso diferente e base desatualizada: 409. Lock de projeto serializa publicações; revisão, projeção, publicada, efetiva e recibo compartilham commit PostgreSQL. Publicada e efetiva são colunas distintas; avançam juntas sem efeito externo. Antes do commit rollback; após commit resultado incerto resolve por replay/consulta de recibo. Revisões e recibos são append-only por trigger; projeção JSON é derivada dos bytes.

Sessões bearer aleatórias de 256 bits vêm exclusivamente de comando administrativo local com acesso ao banco; só SHA-256 é armazenado. Validade absoluta 8 horas, sem renovação implícita; revogação por comando local e DELETE /api/v1/session. Não há senha, cookie, federação ou provedor externo. CLI grava token uma vez em arquivo novo com modo 0600; nunca em stdout. HTTP só loopback; exposição remota exige terminação TLS e revisão operacional fora desta fatia. viewer lê; operator e admin leem/publicam; admin não concede papéis pela API nesta fatia. Grants e recursos são provisionados por operador confiável do banco/CLI. Autenticar antes de consultar projeto; sem grant retorna 404 tanto para projeto existente quanto ausente; viewer publicando recebe 403. Bloquear sessão/grant durante transação impede revogação concorrente atravessar o commit.

Referências repository/commit precisam existir no Git local controlado, estar cadastradas no projeto e não requerer credencial. Só CLI administrativo cadastra repositórios, com caminho canônico, e verifica commit real; API não acessa caminhos arbitrários recebidos. Registro representa snapshot admitido, não garantia de disponibilidade futura. Campos de segredo/credencial continuam proibidos; recursos que dependem deles não são suportados. Não há detecção genérica de segredo em script; AC-01 permanece sem aceite quanto a segredos.

Em erros, requestId é correlação gerada pelo Server; nos recibos é a chave de idempotência enviada pelo cliente. Erros JSON code/message/requestId: 400 envelope/rota malformado; 401 sessão ausente/inválida/expirada/revogada; 403 papel insuficiente; 404 recurso invisível/ausente; 409 base/request ID conflitante; 413 corpo >128 KiB ou YAML >64 KiB; 422 YAML/schema/referência inválidos. Erros internos 500 são genéricos sem dados de entrada. Respostas privadas Cache-Control: no-store. Limites de parser existentes continuam vigentes.


## Contrato T004 — fila e protocolo Server v1

Submissão POST /api/v1/projects/{project}/runs: envelope estrito {requestId, revisionId}, revisão positiva existente (inclusive revisão histórica publicada). Recibo imutável {requestId, runId, revisionId, configHash, commit}. Escopo de repetição identidade/projeto; mesma revisão retorna mesmo recibo, divergência 409; retenção indefinida. Não recebe hash, commit ou configuração do cliente. GET .../run-receipts/{requestId} consulta recibo próprio; viewer consulta GET .../runs e .../runs/{runId}, incluindo tentativas, intenções e recibos. operator/admin submetem e POST .../runs/{runId}/cancel com {}. Terminal retorna {effective:false,state}; em fila cancela imediatamente; assigned/running persiste intenção até confirmação ou perda de lease. Conclusão posterior à intenção resulta cancelled, mesmo se Agent reportar sucesso. Após commit incerto, consultar/repetir antes de executar nova ação.

Credencial Agent aleatória separada é provisionada por CLI local `provision-agent NAME PROJECT FILE`; um Agent pertence a um projeto, Linux, um slot. POST /api/v1/agent/session com bearer de credencial e {protocolVersion:1,platform:"linux",slots:1} cria token de sessão aleatório retornado uma vez, validade absoluta 8h. Sessão nova invalida a anterior; resposta perdida exige nova sessão. Credencial não autentica rotas de usuário ou de trabalho; sessão de usuário não autentica Agent. POST /api/v1/agent/reserve com {} retorna {attempt:null} ou {attempt:...}; replay antes de running retorna a mesma reserva ativa. Antes de executar, reconexão consulta GET /api/v1/agent/attempts/{id}; GET /api/v1/agent/attempts lista histórico da própria identidade, inclusive sessões anteriores e recibos, mas não confere autoridade para mutar tentativas antigas.

POST /api/v1/agent/attempts/{id}/{heartbeat|running|result}: heartbeat/running recebem {fence}; result recebe {fence,outcome,exitCode}, outcome succeeded/failed/timed_out/cancelled/preparation_failed, exitCode inteiro i32 ou null. Sucesso exige exitCode=0; failed exige nonzero; demais null. Preparation_failed somente assigned, demais resultados somente running, salvo confirmação cancelled após intenção em assigned/running. Preparation_failed mapeia run failed; não há retry. Running idempotente; heartbeat tem efeito de renovar para 30s a partir do relógio PostgreSQL, sem ampliar validade da sessão. Cada tentativa tem ID, ordinal 1..2, sessão, fence global crescente, leaseUntil, recibo de reserva e recibo de resultado separado. Replay de resultado exige sessão vigente e fence original, devolve recibo persistido mesmo após expiração do lease; payload distinto 409. Resultado de tentativa expirada sem recibo aceito é 409.

Todas as mutações operacionais usam o mesmo lock transacional PostgreSQL, seguido de relógio `clock_timestamp()` capturado após espera e autenticação. Comparações usam esse instante, inclusive reconciliador. Lease vencido não renova; sessão vencida/substituída perde autoridade imediatamente. Reconciliação periódica e antes de reserva marca tentativa lease_lost, preserva histórico e recibo; volta à fila apenas na primeira perda sem cancelamento. Segunda perda termina failed com causa attempts_exhausted. Cancelamento pendente termina cancelled na reconciliação. Sessão substituída libera tentativa na reconciliação; não espera lease. Terminal nunca volta à fila. Índices únicos parciais protegem trabalho e slot ativos. Não há retry por falha de script, timeout ou preparação. Ausência de despacho não perde trabalho: a reserva é recuperável por consulta, sem afirmar exactly-once externo.

Erros e envelope/no-store seguem REQ-03; 409 autoridade/transição/payload obsoleto; 422 capacidade/protocolo não suportado. Failpoints só em feature de testes: antes de commit rollback/exit; depois de commit desconexão. Agent cliente, execução, logs, artefatos e UI permanecem T005/T006. Trabalhos com credenciais continuam rejeitados pelo schema vigente.

O reconciliador periódico pode ser pausado por EC_TEST_PAUSE_RECONCILER=1 exclusivamente em build test-failpoints; startup/reserva continuam reconciliando. Build operacional ignora essa variável e os headers de falha. A evidência usa isso para provar expiração antes de qualquer reconciliação.

## Contrato T005 — REQ-05 (antes da implementação)

Bootstrap: executável Linux recebe somente caminho de arquivo de configuração local JSON 0600, fora do YAML, contendo endpoint loopback, credentialFile, root e repositories (allowlist de caminhos canônicos). Token nunca entra no argv ou ambiente do script. Um lock de instância sob root impede Agents concorrentes. Sessão nova não recupera autoridade anterior. Journal e spool são arquivos privados sincronizados; falha de escrita impede execução/finalização. Lock herdado bloqueia novo trabalho enquanto descendentes cooperantes sobrevivem; após liberação, a sessão nova consulta o histórico e reconcilia o journal sem mutar tentativa antiga. PID isolado não autoriza matar processo.

Script: /bin/sh -c, cwd checkout próprio por tentativa, env_clear com PATH=/usr/bin:/bin e HOME no workspace. Git local sem rede, hooks, submódulos ou credenciais; checkout detached do SHA completo e HEAD verificado. Running confirmado precede spawn. Processo em grupo próprio; SIGTERM, graça de 2s, SIGKILL e reap. Descendentes que escapem do grupo não são workloads admitidos. Timeout monotônico; heartbeat independente a cada 2s e parada conservadora após 10s sem confirmação. Não há retry local do script.

Rotas Agent adicionais /api/v1/agent/attempts/{id}/{logs|artifact-start|artifact-chunk|artifact-finish|finish}, POST, e GET .../output. Cada mutação contém fence. Logs: {fence,sequence,stream,data}, step implícito 1, sequence global contíguo desde 1, stream stdout/stderr, data hex de bytes brutos (UTF-8 inválido preservado; apresentação deverá escapar controles e usar substituição). Sem ordem causal entre streams; sequência representa ordem de recepção pelo coletor. Máximo 64 KiB/chunk, 16 MiB/tentativa; truncamento explicitado no finish. Confirmação contém sequence e bytes, persistida com payload. Replay idêntico retorna recibo mesmo após término/lease; inclusão exige autoridade ativa. Payload divergente ou lacuna retorna 409. GET output resolve respostas perdidas.

Artefato: start {fence,size,sha256}; chunks {fence,sequence,data}, até 64 KiB, total 16 MiB; finish {fence} verifica tamanho e SHA-256 e publica recibo imutável. Staging fica no mesmo PostgreSQL, evitando autoridade externa de blob. GET output retorna logs, staging e artefato íntegro; usuário GET /api/v1/projects/{project}/runs/{run}/attempts/{attempt}/output exige grant de leitura. Dados são hex, inclusive download. Upload parcial nunca é publicado. Repetição divergente 409. Arquivo ausente, inválido, alterado, ilegível ou excedido é registrado em output.artifactError; não implica sucesso de entrega.

Finish: {fence,outcome,exitCode,output}; output {lastSequence,truncated,artifactError,signal}. Exige sequência final confirmada e, sem artifactError, artefato publicado. Resultado/recibo e confirmações estão na mesma autoridade transacional. failed pode ter exitCode null somente com sinal positivo em output.signal; não inventar exit code. Endpoint result legado permanece compatível com T004 e não declara completude de saída. Sessão vigente e proprietário são exigidos também no replay; novas mutações exigem lease/fence/sessão/estado ativos atomicamente sob guard de orchestration.

Spool: até 16 MiB de bytes, drenagem continua após limite com marcador truncated. Falha de disco é erro explícito, nunca completude. Entrega limitada por autoridade e deadline; retries de transporte repetem somente payload persistido. Reinício cria sessão nova, consulta histórico e não reexecuta para recuperar entrega. Efeitos externos podem repetir sob retry do Server por lease perdido; não há exactly-once nem isolamento.

Limite adicional de spool/ingestão: o Agent agrega leituras parciais em chunks de 32KiB por stream (mais cauda no EOF), limitando arquivos a aproximadamente 514 chunks para 16MiB. O Server rejeita chunks vazios e sequence acima de 2048 por coleção (logs ou partes do artefato), evitando amplificação ilimitada de metadados por mensagens vazias. Rejeição é explícita; nenhum marcador de completude é emitido para entrega rejeitada.


## Extensões HTTP T006 (especificadas antes da implementação)

GET /api/v1/session retorna identity e expires (texto timestamptz); GET /api/v1/projects retorna projects [{project,role,published,effective}] somente dos grants da identidade autenticada. GET /api/v1/projects/{project}/agents retorna agents [{name,revoked,sessionValid}] sem credenciais, tokens ou IDs de sessão. sessionValid é observação da validade da sessão no banco, não heartbeat nem elegibilidade garantida.
POST /api/v1/projects/{project}/validation recebe exatamente {yaml}; viewer também pode validar. Retorna {valid,projection?,diagnostic?}, com code/message/line/column ou field. Usa parser/schema reais, confere project, sem consultar/admitir repositórios nem persistir, executar ou publicar. Referências externas continuam verificadas na publicação. Diagnóstico inválido retorna 200 valid=false; envelope 400, limites 413. Todas as rotas exigem sessão válida (401); projeto invisível 404; mutações vigentes continuam 403 para viewer. Cache-Control no-store. Sem CORS ou credencial Agent no browser.
