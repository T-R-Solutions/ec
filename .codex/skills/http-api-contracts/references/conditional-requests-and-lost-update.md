# Conditional Requests: Validators, Lost Updates and Atomicity

Per RFC 9110 section 13, `If-Match` checks a representation validator before a state-changing action. For a resource with a strong entity tag, a stale `If-Match` normally yields **412** and no change; `If-Match: W/"..."` cannot pass the strong comparison. An origin may require a conditional update and return **428** under RFC 6585. `If-None-Match` on GET can yield **304**, without a representation body; do not treat a 304 as an update success. In production, evaluate preconditions atomically with the state transition in the authoritative persistence layer: simply comparing an in-memory ETag and later issuing a separate UPDATE can still lose updates.

Test two clients with the same initial ETag concurrently: exactly one expected successful update under the chosen replace contract, and the other receives a stale precondition error; verify final state. Do not claim this synthetic reference test certifies database isolation or distributed transactions. Distinguish `409` for domain-state conflict or duplicate idempotency-key misuse from `412` for failed HTTP precondition. ETag may change when representation changes; do not assume its encoding is a database primary key. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), [RFC 6585](https://www.rfc-editor.org/rfc/rfc6585.html).
