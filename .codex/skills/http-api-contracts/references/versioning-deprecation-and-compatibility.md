# API Versioning, Deprecation and Consumer Compatibility

No IETF HTTP RFC mandates `/v1` path versioning over headers or other forms; version location is a product choice with tooling, caching, discovery and rollout implications. Explicitly record major/minor compatibility expectations, supported client populations, change propagation, migration window, old-client tests and rollback plan. OpenAPI diffs can detect syntax changes but not hidden validation, authorization, concurrency or result-order changes. For a possibly breaking update, require actual supported consumer evidence, not only a SemVer label.

RFC 9745's `Deprecation` uses an HTTP Structured Field date, e.g. `Deprecation: @1688169599`. RFC 8594's `Sunset` is an HTTP-date hint and does not guarantee a shutdown date. They are distinct signals; neither silently changes resource semantics. Communicate replacement links and test old clients during a defined overlap. Science S-01/S-02 describes widespread versioning variation and discrepancies between claimed SemVer and detected breaking changes, not an optimal version scheme. [RFC 9745](https://www.rfc-editor.org/rfc/rfc9745.html); [RFC 8594](https://www.rfc-editor.org/rfc/rfc8594.html); [S-02](https://doi.org/10.1007/978-3-031-62362-2_25).
