## Evidence-to-method synthesis

| Engineering question | Basis | Bounded implementation decision | What must come from an approved Ec spec |
|---|---|---|---|
| What identifies a federated person? | O01–O03, A01 | Map verified `(iss,sub)` or scoped SCIM IDs to a local stable ID; never merge solely by email or display name | Allowed providers, account linking, identity migration and merge policy |
| Is an invitation a membership? | N1, O24–O25, O07, A08 | Operational invitation token/state; accept only verified subject, then follow approved binding/publication workflow; no automatic claim from pending | Actual invite TTL, allowed domains, acceptance behavior, onboarding approvals |
| Who can assign roles? | O10–O11, A01–A06, A09 | Distinguish admin authority to edit a target from scope/role delegation; preflight and re-check candidate, require independent approval only when policy calls for it | Exact role taxonomy, can-grant predicates, separation rules, emergency access |
| Can an IdP automatically edit Ec desired policy? | N1, O02–O05, O22–O23, A07 | Provider authoritative for identity facts if configured; map external events to reviewed desired-state changes or an approved trusted reconciliation path; no silent second source | Provider-of-record, local override hierarchy, sync conflict resolution |
| How is access revoked after disabling identity? | N1, O07, O11–O12, A07–A08 | Immediate trusted deny/mitigation for disabled principal, separately reconcile YAML bindings; reactivation must not silently grant from stale policy without explicit decision | Actual live deny mechanism, token expiration risk, reactivation/restoration policy |
| What does Git publication mean? | N1, O16–O18, A07 | Distinguish candidate, authorized, published desired, and acknowledged effective; never mark synchronized from an untrusted cache | Exact Git repository, receipt, reconcile and audit contracts |
| How is the matrix rendered? | N2, O19–O20, A09 | Show direct assignment and effective permissions separately; accessible controls, target/scope confirmation, keyboard focus | UI design system, which assignment edits supported by each mode |
| How is safety tested? | O11, O16, A04–A07 | Model-based negative cases, stale candidate/approval/replay, integration and browser accessibility tests | Actual API/DB/schema fixtures and acceptance evidence |

## Unresolved decisions, conflicts and limitations

- **No internal conflict** found between the two consulted Ec norms. Both require canonical YAML desired configuration, correct authorization and truthful UX; passwords/sessions/invitations remain operational.
- **Important design tension:** external group provisioning may be source-of-record for the *identity-provider observation*, but it must not silently replace Ec's canonical desired policy. The approved SDD feature must choose a mapping/reconciliation contract and specify whether memberships are provider-managed or locally managed. This is an unresolved **product design decision**, not a norm conflict.
- **No Ec role names, inheritance, provider precedence, invitation lifetime, approval threshold, emergency account policy, default membership, or reactivation restoration rule** was invented. The synthetic reference model chooses flat teams and illustrative `'viewer'`/`'admin'` for testing only.
- Vendor differences (GitHub, GitLab, TeamCity, Keycloak) are deliberately compared, never imported as Ec behavior; standards have versions and optional features.
- Publication pages do not prove complete access to each work. Some publisher research and one book were metadata-only. No work is claimed read completely when only portions were inspected; no forums consulted.
- No actual Ec server, IdP, authorization decision point, YAML parser, Git source-of-truth, PostgreSQL instance, browser UI or agent benchmark was provided. **No functional deployment, performance or real security claim can be made.**
