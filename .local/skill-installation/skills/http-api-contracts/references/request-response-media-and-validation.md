# Request / Response Representations and Validation

Define per request: path/query/header/body names and cardinality; required/optional/null semantics; types, sizes, allowed values, unknown fields, nested reference handling and error behavior. Define `Content-Type` media-type matching before parsing a body and `Accept` response content negotiation independently. `415 Unsupported Media Type` concerns an unsupported request representation, `406 Not Acceptable` concerns response negotiation; `400 Bad Request` concerns malformed syntax, while `422 Unprocessable Content` may describe a syntactically valid body violating semantic constraints. Those choices must be documented and tested rather than guessed.

A JSON API response is an HTTP wire payload and not automatically a JSON configuration file. Keep a canonical product configuration file format according to the destination norm. For JSON Schema draft 2020-12, validate actual request/response schemas separately from OpenAPI document structure; `required`, `additionalProperties`, `null` and format handling require tool-specific precision. When an API contains secrets use references and redaction in logs. Capture representative positive/negative bodies and correct `Location`, `ETag`, `Vary`, cache and correlation headers. Test missing `Content-Type`, unsupported `Accept` and incompatible media parameters. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html); [JSON Schema](https://json-schema.org/draft/2020-12); [OWASP REST](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html).
