# HTTP API Security and Authorization Boundaries

Authorization is decided on the backend for every actor/action/object, not inferred from a visible UI route or a syntactically valid bearer token string. Distinguish authentication 401, authorization 403 and deliberate obscuring 404 according to approved privacy policy. Scope collection queries, cursor tokens, ETags, links and replay keys by authorized tenant/resource. Avoid trusting caller-supplied tenant headers and URL IDs without resource-level checks. No API method is implicitly authorized because the HTTP verb is normally safe. Apply payload size limits and parser limits; avoid raw technical error leakage.

Threat-test: horizontal cross-object/tenant access; replay by another principal; forced browsing and method override; cursor swapping and tampering; 401/403/404 leaks; cache contamination; malformed media types; HTTP smuggling at proxies when relevant; excessive payload and request budgets. Use OWASP's REST Security Cheat Sheet and API Security Top 10 as **guidance**, and derive specific controls from the product threat model. Dummy fixture bearer strings are a test driver, **not real authentication**. [OWASP REST](https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html); [OWASP API Top 10](https://owasp.org/API-Security/editions/2023/en/0x11-t10/).
