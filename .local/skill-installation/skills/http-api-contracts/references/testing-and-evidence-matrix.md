# Positive, Negative and Boundary Oracles

> Use the destination's existing requirements and evidence format; named workflow documents are examples, not prerequisites. Optional SDD mapping is configured outside this skill. Commands, fixture paths and historical execution claims from the source package are illustrative or imported evidence unless the corresponding files are present and independently checked; they are not current test results or bundled executable tools.

For each endpoint publish a matrix of `(method, URI, actor, headers, body, expected status, expected headers/body, side effects, timeouts)` linked to project acceptance criteria. Use independent consumer and provider oracles; do not only assert schema acceptance. Minimum families when applicable: valid create/read/update, 401/403/hidden 404, invalid syntax 400, semantic validation 422, unsupported media 415, unsatisfied Accept 406, precondition required 428, stale precondition 412, domain conflict 409, 304 without body, 201 Location, 202 pending monitor, 429 Retry-After, malformed or reused idempotency key, pagination scope/limit/cursor tampering, method 405 `Allow` and content-type safety.

Run concurrent updates and duplicate requests (including after simulated failures) in a real provider fixture with persistent storage when claims depend on transactions. Test replay TTL, crash recovery and pagination consistency under mutations in the **actual** service; an in-memory fixture cannot verify these. Mutate response/status/headers one at a time and require oracle failure to show sensitivity.
