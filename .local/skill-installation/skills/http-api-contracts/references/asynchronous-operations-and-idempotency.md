# Asynchronous Acceptance, Replay Keys and Retry Semantics

`202 Accepted` (RFC 9110) means a request has been accepted for processing, not that effects have completed. Publish a status URL or another observable confirmation contract, status transition names, expiration, cancellation rules, permissions and poll/backoff guidance. A client should not show completed success based solely on a 202. If a `Location` points to operation status, that is an **application convention**; distinguish it from the 201 creation of a resource.

PUT and DELETE are idempotent by HTTP method semantics; unsafe retries of POST/PATCH require explicit published guarantees. `Idempotency-Key` **-08** (2026-10-22) is an *Internet-Draft*, not final standards-track RFC. If chosen, follow the draft's quoted Structured Field String syntax (or document a different contract clearly). The loopback model recognizes only simple quoted ASCII token characters, not full RFC 9651 escaping or future draft changes. Document the key's uniqueness/scope, payload fingerprint, replay response, in-flight conflict, TTL, storage durability, recovery and mismatch behavior. A key does not ensure exactly-once effects against external systems. Contract replay tests must include a different body with the same key and a replay after a timeout. Use bounded retries, `Retry-After` where supplied, jitter where justified, and avoid implicit re-execution after ambiguous failure. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html); [Internet-Draft](https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-08).
