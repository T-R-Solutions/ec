# HTTP Caching, Cache Privacy and Validators

Document whether each representation may be stored by a user-agent cache, private intermediary or shared cache. RFC 9111 distinguishes `private`, `no-store`, `no-cache`, `max-age`, validation, freshness and stale allowances. `no-store` instructs compliant caches not to store the message, but **does not provide encryption or a privacy guarantee**. Authenticated response cacheability requires reviewing Authorization and shared cache restrictions; do not blindly mark user-specific data public. `Vary` is part of cache selection and cannot compensate for a broken authorization policy.

ETag validators can reduce bandwidth and protect mutable resources when tied to an actual representation/revision. `If-None-Match` GET + 304 differs from an unsafe conditional write with `If-Match` + 412. Test no stale state disclosure across logout/identity switch, old response races, 304 bodylessness, validator precedence, data-scope changes and intermediary behavior where available. HTTP caches and frontend data caches must be reviewed separately. [RFC 9111](https://www.rfc-editor.org/rfc/rfc9111.html); [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).
