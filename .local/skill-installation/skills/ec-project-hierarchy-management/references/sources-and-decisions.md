| O4 | GitLab, [Subgroups](https://docs.gitlab.com/user/group/subgroups/) | Key sections read | Nested group membership/access, one parent, and operational depth caveats demonstrate hierarchy effects; GitLab's 20-level limit and five-level advice are **not Ec defaults**. |

| O7 | GitHub, [About Organization Teams](https://docs.github.com/en/organizations/organizing-members-into-teams/about-teams) | Key sections / official source inspected | Nested **teams** inherit access; do not equate team hierarchy with project hierarchy. |
| O8 | GitHub, [Moving a Team in Your Organization's Hierarchy](https://docs.github.com/en/organizations/organizing-members-into-teams/moving-a-team-in-your-organizations-hierarchy) | Key sections read | Moving a team can change inherited repository permissions; moving a node under its own child is rejected. | O9 | PostgreSQL 18, [WITH Queries / RECURSIVE / SEARCH / CYCLE](https://www.postgresql.org/docs/current/queries-with.html) | Key sections read | Recursive CTEs support tree traversal; SQL `CYCLE` supports cycle-sensitive recursive queries. | O10 | PostgreSQL 18, [`ltree`](https://www.postgresql.org/docs/current/ltree.html) | Key sections read | Indexed hierarchical path operations are available; materialized paths entail path rewrite on subtree relocation, and choosing them requires measurements. |
| O11 | PostgreSQL 18, [Constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) | Key sections read | Foreign keys and uniqueness help referential integrity but do **not**, by themselves, enforce absence of arbitrary ancestry cycles. Add a whole-tree validation method. |
| O12 | PostgreSQL 18, [Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html) | Key sections read | `SERIALIZABLE` protects equivalent outcomes of committed transactions and can abort requests requiring a complete retry; it does not enforce every domain invariant without appropriate logic. |
| O13 | PostgreSQL 18, [Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html) | Key sections read | Row/advisory locks and deadlock handling can coordinate concurrent rewrites. Advisory locks are cooperative, not mandatory enforcement. |
| O14 | PostgreSQL, [Row Security Policies](https://www.postgresql.org/docs/16/ddl-rowsecurity.html) | Key sections read (supported v16 page) | RLS restricts SQL row operations in its context; table owners/privileged roles and access via other systems require separate authorization considerations. | O15 | OWASP, [Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html) | Key sections read | Deny by default, least privilege, per-request authorization, appropriate logging/testing. The actual policy engine belongs to Ec access skills. |
| O16 | W3C WAI-ARIA, [Tree View Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/treeview/) | Key sections read | Hierarchical tree navigation supports arrow-key expansion, focus vs selection distinction and tree semantics. A project tree is an accessible interaction, not only a diagram. |
| O17 | W3C WCAG 2.2, [2.5.7 Dragging Movements](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements) | Key sections read | A separate single-pointer non-drag path is required for drag-driven functionality, with keyboard access considered independently. |
| O18 | NIST SP 800-162, [ABAC Definition and Considerations](https://csrc.nist.gov/pubs/sp/800/162/upd2/final) | Official abstract/metadata read | Access decisions can depend on subject, object, operation, environment and policy. Reparenting alters the object relationship context; do not cache an old decision as current. |

## Synthesis and explicit resolutions

| Question | Verified evidence | Practical, **non-normative** engineering resolution | Dependency / uncertainty |
|---|---|---|---|
| What does a project move change? | O1, O5, O6, A1 | Compare old/new ancestors and all derived settings/access plus reference effects before accepting mutation | Actual Ec inheritance table, access engine and resource binding schema absent |
| Are roles, projects, groups one tree? | N1, O3, O7, A2 | Model distinct domain relations with explicit bridges; do not use project ancestry as a substitute role hierarchy | The Ec spec must define actual association contracts |
| Which hierarchy storage works best? | O9–O13, A4, A7 | Use adjacency + recursive query as baseline, then benchmark against `ltree`/closure for representative read/move load | No Ec data model, hardware, expected node counts or benchmarks supplied |
| How prevent a cycle under concurrent moves? | O9, O12, O13, A3 | Enforce validated candidate and appropriate commit-time concurrency boundary; test interleaved moves and full retry | Actual YAML Git commit point and PG state are skill 3 responsibilities |
| How are settings inherited? | N1, O2, O4 | Define per-family, explicit precedence and origin; do not infer secrets/authorization inheritance automatically | Need approved rules for each family, including deny/override behavior |

| How does the UI support moves? | N2, O16, O17 | Provide visual, form and YAML paths to one candidate; non-drag single-pointer and keyboard routes, with explicit impact | UI component details belong to Vue/accessibility skills |

## Conflicts, restrictions and evidence quality

- **No normative conflict found** between N1 and N2 for project hierarchy. Both require visual/form/YAML consistency and verified operational status. They are **not** academic sources; they are project owner decisions.
- GitLab and TeamCity disagree in specific precedence and inheritance behaviors; this is **not a conflict in Ec policy** because neither vendor is the authority. Their examples only establish risks and design alternatives.
- The algorithm papers are not workload benchmarks for Ec. No empirical performance result is extrapolated.
- Some research works were inspected only via abstracts; citations are retained with explicit limits. No full-text access is falsely claimed. No forum or social source was used.
- No actual Ec project schemas, source repo, authorization engine, SDD feature acceptance, live PostgreSQL instance or browser UI was accessible to validate these design choices.
